## 2. 功能详解

- **两个 token 架构是本组件唯一有设计难度的地方**（见 README「两个 token」一节）：Casdoor 只证明身份，应用 token（带 `roles[]`/`dept_path`/`org_id`）由本组件用自己的私钥签。`signAccessTokenFor`（`service.go`）现问 `infra-authz` 的 `ResolveClaims`——**不留 claims 兜底缓存**，`infra-authz` 不可达时登录/刷新会失败（fail-closed，设计计划 §5 的明文决策），但已登录用户做业务不受影响（组件用内存里最后一份 bundle，那是 `be-sdk` 的事，与本组件无关）。
- **refresh token 本身也是一个我们自己签的 JWT**（`tokens.go` 的 `refreshClaims`，带 `typ: "refresh"` 自定义 claim）——好处是验签不需要查库，查库只为确认它没被撤销/没被轮换掉；坏处（已知取舍）是"typ 不对"必须显式校验，否则应用 token 与 refresh token 可能互相冒充（`tokens_test.go` 的 `TestVerifyRefreshToken_不接受应用token冒充` 专门测这一条，且第一版测试用例本身写错过，见测试里的详细注释）。
- **refresh token 轮换 + 重放检测**（`repo/refreshtokens.go` 的 `RotateRefreshToken`）：用一个已经轮换掉的旧 jti 再刷新，不仅这次失败，还会撤销这个 sub 名下**全部**仍然有效的 refresh token——这是 refresh token rotation 的标准配套防护，超出设计计划字面要求，但与 §14.1.6 的语义天然一致。
- **kid 是确定性推导的**（`keys.Thumbprint`，严格实现 RFC 7638，`keys_test.go` 对照官方示例核对过）——同一把签名私钥每次启动都算出同一个 kid，`UpsertSigningKey` 的幂等性建立在这个前提上。
- **JWKS 双挂**：`appTokenPreviousPublicKeyPem` 非空时，`/.well-known/jwks.json` 同时暴露新旧两把公钥（`kid` 区分），刷新路径的 `Verifier` 同样接受两把钥匙签的 refresh token——密钥轮换期间旧 token 不会立刻失效。
- **webhook 是"严格认证 + 宽容解析"**（`service.go` 的 `HandleWebhookDelivery`）：共享密钥 header 校验失败直接 401；payload 解析失败/认不出 action/找不到用户标识都不报错，只把这条投递标记 `ERROR`/`IGNORED` 存档——Casdoor 的 webhook payload 形状未能在本次调研里 100% 确认（见 AGENTS.md「已知缺口」），过度严格的解析会把"格式没跟上"变成"用户事件整体丢失"。
- **去重判据是显式 `SELECT EXISTS`，不是让 `INSERT` 撞唯一约束**（`repo/webhookdeliveries.go`）——`webhook_deliveries` 按 `received_at` 分区，分区表的唯一索引必须包含分区键，`(dedup_key, received_at)` 这个组合对两次真实间隔的重投形同虚设，第一版实现踩过这个坑（见 `docs/dev/实测踩坑记录.md` C9）。
- **自举是"每次启动都对账"**，不是"只跑一次"（`bootstrap/bootstrap.go`）：每一步先查 Casdoor 里那个对象是否已存在，存在就跳过创建，只把本地 `bootstrap_state` 补齐；不存在才创建。单步失败不阻断其它步骤，下次启动重新对账一遍。
- **OIDC 发现失败会重试直到成功**（`module.go` 的 `discoverIDTokenVerifier`）——Casdoor 可能比本组件启动得晚，指数退避封顶 30 秒；成功一次之后 `keyfunc` 自己的后台刷新协程接管 JWKS 的持续更新，这个循环就退出了。

## 3. 完整契约清单

**gRPC `infra.iam.v1.IamService`**（2 个 rpc，见 `contracts/infra/iam/v1/iam.proto`）：

| rpc | 类型 | 说明 |
|---|---|---|
| `BatchGetUsers` | 读，§3.8 强制的 batchGet | 逐个回源 Casdoor 查（`GET /api/get-user?userId=<uuid>`），查不到的 sub 直接省略 |
| `GetTenantFeatures` | 读 | gRPC 版的 features 清单，内容与 REST 完全一致 |

**REST**（见 `contracts/iam.openapi.yaml`，路径**不走** `/{domain}/{name}/**` 前缀）：

| 路径 | 权限键 | 说明 |
|---|---|---|
| `POST /api/iam/token` | `besdk.Public` | 换应用 token |
| `POST /api/iam/token/refresh` | `besdk.Public` | 刷新 |
| `POST /api/iam/logout` | `besdk.Authenticated` | 作废当前 refresh token |
| `GET /.well-known/jwks.json` | `besdk.Public` | 不进 `edge_routes`，只供其余组件的 `iamJwksUrl` 内网直连 |
| `GET /api/tenant/features` | `besdk.Public` | 前端启动时拉 |
| `POST /api/iam/webhooks/casdoor` | `besdk.Public` + 共享密钥 header | 不进 `edge_routes`，只供 Casdoor 带外容器直连 |

**发布事件：** `infra.iam.user.created/updated/disabled.v1`（核心，供 `infra-notification` 维护通知快照）、`infra.iam.login.v1`（旁路，仅供未来 `infra-audit`）。
**消费事件：** `infra.authz.user_role.changed.v1`（仅 `change_type: kicked` 时作废该用户全部 refresh token）。

详细字段与判据见设计计划 `docs/design/infra-iam-casdoor.md`——那份是真相源，这里是速查表。

## 4. 数据模型

| 表 | 分区 | 唯一约束 | 说明 |
|---|---|---|---|
| `refresh_tokens` | 不分区 | `jti` 主键 | 按在线人数有界；`revoked_at` NULL = 仍有效；`rotated_from` 记轮换链 |
| `signing_keys` | 不分区 | `kid` 主键 | 只有元数据（kid/alg/时间戳），私钥本身不落库 |
| `webhook_deliveries` | `received_at` **月**分区 | `(dedup_key, received_at)`（去重判据用显式 `SELECT EXISTS`，不依赖这条约束，见上） | `payload` 是 `TEXT` 不是 `JSONB`——JSONB 列写入时校验合法性，不合法 JSON 的投递体会让 INSERT 直接失败，与"宽容存储"的设计意图矛盾（`docs/dev/实测踩坑记录.md` C10） |
| `bootstrap_state` | 不分区 | `step` 主键 | 单行到个位数行，`detail` 是 JSONB（这张表不存在"存不下"的风险，`detail` 内容永远是应用代码自己拼的合法 JSON） |

另有全组件通用的 `event_outbox`/`event_inbox`（周分区）——本组件是本阶段少数既发布又消费事件的 infra 层组件。

**实测验证**（真跑在 `infra_iam_casdoor` schema + 真实 Casdoor 容器 + 真实 `infra-authz` 容器，非 mock）：refresh token 签发/轮换/重放检测/连坐撤销、登出幂等且只能作废自己的 token、签名密钥元数据幂等登记、bootstrap 三步幂等可重跑（含"webhookCallbackUrl 留空时跳过"分支）、webhook 投递去重与"publish 失败整体回滚"、Casdoor 管理 API 全套（建组织/应用/webhook、按 sub 查用户）、OIDC 发现 + JWKS 验签（含 issuer 校验、签名篡改拒绝）、**端到端**（`ExchangeToken` → `RefreshToken` → `Logout` 全链路对着真实 `infra-authz` gRPC 走一遍，见 `service_test.go` 的 `TestExchangeTokenAndRefreshToken_端到端对着真实infra_authz走一遍`）。

## 5. 开发

```bash
export TEST_PG_DSN="postgres://postgres:<密码>@localhost:5432/brickkit_test_db?sslmode=disable&search_path=infra_iam_casdoor,infra_iam_casdoor_archive"
export TEST_CASDOOR_BASE_URL="http://localhost:8000"                    # 可选：跳过则对应真机测试自动 Skip
export TEST_INFRA_AUTHZ_GRPC_ENDPOINT="http://<infra-authz 容器 IP>:9223" # 可选：同上
go test ./... -race -count=1
```

跑测试前必须先用真的迁移工具把 `infra_iam_casdoor` schema 建出来：

```bash
export DATABASE_USER=postgres DATABASE_PASSWORD=<密码> DATABASE_HOST=localhost DATABASE_PORT=5432 DATABASE_NAME=brickkit_test_db PG_SCHEMA=infra_iam_casdoor
go run ./backend/cmd/migrate up
```

`TEST_INFRA_AUTHZ_GRPC_ENDPOINT` 拿容器 IP 的方法（`infra-authz` 的 gRPC 端口默认不映射到宿主机）：

```bash
docker inspect <infra-authz 容器名> --format '{{json .NetworkSettings.Networks}}'
# Docker 默认桥接网络允许宿主机直接连容器内部端口，不需要显式 publish
```

**核心测试**是 `service_test.go` 的 `TestExchangeTokenAndRefreshToken_端到端对着真实infra_authz走一遍`——改 `signAccessTokenFor`/`RotateRefreshToken`/`Logout` 任何一个环节后都应该重跑这条测试确认全链路仍然打通。

`repo_test.go`/`bootstrap_test.go` 用带时间戳的 `uniqueID` 前缀构造 sub/jti/kid/组织名，测试之间互不干扰；但 `bootstrap_state` 的三个 step 名（`casdoor_org`/`casdoor_app`/`casdoor_webhook`）在表结构上是**全局单例**——`bootstrap_test.go` 里跨测试共享这几行时要留意清理顺序（见该文件内注释）。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| `POST /api/iam/token` 一直返回 503「Casdoor 验证器尚未就绪」 | `discoverIDTokenVerifier` 还没成功过一次——检查 `casdoorBaseUrl` 是否可达、Casdoor 是否已经完全启动（`/api/health`） | 等待重试循环成功；确认 `casdoorBaseUrl` 配的是**从本组件视角**能访问到的地址（brickkit 管理的容器要用 `host.docker.internal`，不是 `localhost`） |
| `keyfunc` 报 `invalid HTTP status code: 404`，日志里的 `url` 缺少端口 | Casdoor 的 `origin` 配置（`conf/app.conf`）本身漏配了端口——OIDC 发现文档的 `issuer`/`jwks_uri` 都是从这个配置值拼出来的（`docs/dev/实测踩坑记录.md` C8） | 检查 Casdoor 的 `origin` 配置是否带端口，不是本组件代码的问题 |
| `RotateRefreshToken` 对一个"看起来合法"的 refresh token 也报 `ErrRefreshTokenInvalid` | 这个 jti 之前已经被轮换过一次（正常的重放检测生效），或者这个 sub 名下所有 token 被连坐撤销过（触发过一次重放检测，或被踢人事件撤销过） | 这是设计行为，不是 bug——前端应该在收到 401 后引导用户重新走一遍登录流程，不是重试同一个 refresh token |
| 建应用/组织/webhook 时 Casdoor 返回 400 `unsupported_grant_type` 或类似 | 混淆了"生产用的应用"（`CreateApplication`，不含 `password` grant type）与"仅供测试签发 token 用的应用"——生产应用永远不该加 `password` grant type，浏览器走 `authorization_code` 直连 Casdoor | 检查调的是哪个建应用的路径；测试专用的建应用逻辑在 `casdoor_integration_test.go` 的 `createTestAppWithPasswordGrant`，不要把它误用到生产代码 |
| webhook 投递重投两次，`webhook_deliveries` 里却出现两条记录 | `dedup_key` 的去重判据用了 `INSERT ... ON CONFLICT`/让 `INSERT` 撞唯一约束——分区表的唯一索引必须包含分区键 `received_at`，两次重投的 `received_at` 几乎必然不同，唯一约束形同虚设 | 去重必须走显式 `SELECT EXISTS(... WHERE dedup_key = $1)`（不带 `received_at` 条件），`repo/webhookdeliveries.go` 的 `RecordDeliveryAndPublish` 已经是这么写的，不要改回撞约束的写法 |
